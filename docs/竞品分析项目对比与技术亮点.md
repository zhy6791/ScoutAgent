# 竞品分析项目对比与技术亮点

> 文档性质：基于源码的竞品项目技术对比。
> 
> 对比对象：
> - [competitorsmart](https://github.com/t0moon/competitorsmart)
> - [competitive-intelligence-multi-agent](https://github.com/bcefghj/competitive-intelligence-multi-agent)
> - 当前项目：`VerdaAI-Investigator`
> 
> 核对时间：2026-10-22。
> 
> 评价口径：
> - **已实现**：源码中存在完整调用链，能够说明该能力已进入运行流程。
> - **部分实现**：存在代码、接口或工作流骨架，但仍缺少关键持久化、调度或下游接入。
> - **架构声明**：主要出现在 README、架构文档、配置或依赖中，当前源码不足以证明功能已经运行。

## 1. Executive Summary

两个参考项目与当前项目的侧重点不同：

| 项目 | 主要优势 | 当前源码中最值得关注的能力 |
|---|---|---|
| `competitorsmart` | 自主研究 Agent | LangGraph ReAct 工具循环、报告完整性终止条件、Playwright 视觉取证、DOCX 导出 |
| `competitive-intelligence-multi-agent` | 持续竞品情报原型 | 变化检测、严重程度告警、Battlecard、多 Agent 模块拆分、质量分循环 |
| `VerdaAI-Investigator` | 证据与质量控制 | Evidence ID、品牌证据对齐、规则检查 + LLM 复审、分类返工、舆情采集、Trace、SQLite 资产沉淀 |

当前项目缺少的主要能力集中在四类：

1. **自主工具使用**：模型不能在同一个研究回合中自主决定是否继续搜索、换关键词、打开页面或截图。
2. **写后成稿门禁**：当前质检主要发生在写作前，缺少针对最终报告正文的完整性校验。
3. **持续监控**：已有竞品订阅 CRUD，但没有完整的定时抓取、页面快照、版本 Diff 和变更告警链路。
4. **销售交付形态**：没有独立的 Battlecard 资产，也没有 DOCX 导出和外部通知。

这不意味着参考项目整体优于当前项目。当前项目在证据追踪和返工语义上更细：Claims 必须绑定 `evidence_id`，证据有品牌归属，规则检查和 LLM 复审共同决定是否返工，并且 `collect`、`analyze`、`write` 问题有不同处理路径。

## 3. `competitorsmart` 的亮点

### 3.1 真正的 LangGraph ReAct 工具循环

`src/agent/graph.py` 构建了如下图：

```text
START
  ↓
agent
  ├─ 有 tool_calls → tools → agent
  └─ 无 tool_calls 且报告完整 → END
```

绑定到 LLM 的工具包括：

- `search_web`：通过 DuckDuckGo/DDGS 检索公开网页；
- `fetch_webpage`：抓取网页并清洗正文；
- `screenshot_webpage`：通过 Playwright 打开页面并保存截图。

模型每次收到工具结果后，可以再次产生工具调用。这样，搜索、抓取、补充检索和页面截图由模型根据当前上下文决定，而不是只能按照固定的步骤执行。

当前项目的 `run_pipeline()` 按阶段固定调用搜索、抓取、分析和写作。模型会参与计划、分析、复审和写作，但不能在一个分析回合中自主调用工具并决定下一步研究动作。因此当前项目属于中心编排器驱动的多阶段流水线，不是通用 ReAct Agent。

**成熟度：已实现。**

### 3.2 报告完整性作为终止条件

`_report_is_complete()` 在 Agent 产生无工具调用的文本后执行检查，主要检查：

- 标题是否以指定格式开头；
- 报告正文是否达到至少 4000 字；
- 11 个固定章节是否全部存在；
- 来源 URL 数量是否达到最低阈值；
- 每个竞品是否有至少 8 个字段；
- 市场、能力、商业模式和机会章节是否达到最低要点数量。

检查未通过时，路由不会结束，而是返回 `agent`：

```text
agent 输出报告
  ↓
完整性校验
  ├─ 通过 → END
  └─ 不通过 → agent 继续调用工具或补写
```

当前项目已经有较完整的分析前质量闸门：品牌覆盖、维度覆盖、Schema 完整度、Evidence 引用和 LLM 复审都会在 `audit` 阶段检查。但写作完成后，没有同等强度的成稿级门禁来确认：

- 所有必需章节是否真的写入正文；
- 每个竞品是否在最终章节中出现；
- 报告正文引用的 Evidence ID 是否存在；
- 是否存在空章节、模型错误文本或重复段落；
- 关键 Claims 是否实际进入最终报告。

**成熟度：参考项目已实现；当前项目缺少。**

### 3.3 Playwright 浏览器视觉取证

`src/agent/screenshot_tool.py` 使用 Playwright 访问公开网页，支持首页、功能页和定价页的整页或视口截图。截图文件写入本次运行目录，工具返回可嵌入 Markdown 的图片路径。

实现中的工程约束包括：

- 根据 URL 的 SHA-256 生成稳定文件名；
- 支持 `full_page` 截图；
- 过滤 `localhost`、`.local` 和常见内网地址；
- 浏览器或 Playwright 缺失时返回明确错误；
- 截图与报告运行目录绑定，便于一起归档。

当前项目的 `Evidence` 和模型字段中存在图片/截图相关字段，但采集逻辑主要是从 HTML 提取图片 URL，没有使用浏览器渲染当前页面，也没有将网页视觉状态作为独立证据归档。

这会影响以下调研内容：

- 定价页当前展示的套餐和价格；
- 官网首页的定位文案；
- 产品功能页的界面和能力入口；
- 页面布局、导航和视觉信息架构。

**成熟度：参考项目已实现；当前项目缺少浏览器级截图证据。**

### 3.4 Markdown 到 DOCX 的交付

`src/export_docx.py` 通过 Pandoc 把 Markdown 报告转成 `.docx`，并保留标题、列表、表格及相对路径图片。该功能适合需要将报告发送给客户、管理层或销售团队的场景。

当前项目主要输出 Web 报告 JSON 和前端渲染结果，没有统一的 DOCX 导出接口。

**成熟度：参考项目已实现；当前项目缺少。**

### 3.5 结构化的一方业务资料输入

`competitors_input.json` 支持如下上下文：

```json
{
  "market": "目标市场",
  "product_category": "产品品类",
  "geography": "地域",
  "our_product": "我方产品",
  "website_copy": "官网文案",
  "sales_notes": "销售笔记"
}
```

这些字段可以让 Agent 同时理解：

- 我方产品定位；
- 对比市场和地域；
- 竞品官网公开表达；
- 销售一线遇到的客户问题；
- 竞品资料与内部材料之间的关系。

当前项目的任务入口主要接收自然语言需求和澄清问卷。虽然有市场、用户群体、产出视角等字段，但还没有将“我方产品说明、销售笔记、官网文案、内部异议”作为标准化输入对象。

**成熟度：参考项目已实现；当前项目部分具备，但没有统一的一方资料模型。**

### 3.6 低成本搜索依赖

`competitorsmart` 默认使用 DuckDuckGo/DDGS，不要求 Serper、SerpAPI 或 Bocha Key。其优点是：

- 没有搜索 API Key 时也能运行；
- 没有第三方搜索额度成本；
- 可以作为主搜索服务失败时的 fallback。

当前项目通过搜索服务适配器对接 Serper、SerpAPI 或 Bocha，检索控制和结果结构化更强，但依赖外部服务额度和网络稳定性。

**成熟度：参考项目已实现；当前项目可考虑作为降级搜索适配器。**

### 3.7 PM 方法论技能库

`competitorsmart` 附带较多产品经理方法论文件，涉及竞品分析、定位、用户研究、PRD、定价、增长和销售策略等。

需要区分两件事：

1. 技能文件确实存在，是可复用的方法论资产；
2. 当前主 ReAct 流程并没有证明会自动动态加载所有技能并参与每一轮决策。

因此，这部分应评价为方法论资料库，而不是已经完全接入运行时的智能 Agent 能力。

**成熟度：资产已实现，运行时自动调用未确认。**

### 3.8 安全细节

该项目还提供了几个可借鉴的工程细节：

- `.env` 的预提交防泄露约束；
- 错误信息脱敏；
- 截图工具对公网 URL 和内网地址的过滤；
- 工具失败时给出可操作的错误提示。

这些不是竞品分析业务功能，但对于联网 Agent 的生产化有直接价值。

## 4. `competitive-intelligence-multi-agent` 的亮点

### 4.1 竞品页面变化检测

`MonitorAgent` 会读取竞品官网、定价页、招聘页和博客等 URL，执行以下处理：

```text
抓取网页
  ↓
计算 SHA-256 Hash
  ↓
与 previous_hashes 比较
  ├─ 相同 → 跳过 LLM 分析
  └─ 不同 → 提取文本、价格、职位 → LLM 分类
```

LLM 输出 `CompetitorChange`，包含：

```json
{
  "change_type": "pricing | product | hiring | news",
  "severity": "low | medium | high | critical",
  "title": "变化标题",
  "summary": "变化摘要",
  "url": "来源 URL",
  "detected_at": "检测时间"
}
```

这比单次调研多了一层时间维度：系统关注的不是“当前竞品是什么样”，还包括“竞品最近发生了什么变化”。

但是，源码核对发现该能力仍有边界：

- API 每次运行时将 `previous_hashes` 初始化为空；
- 没有找到页面 Hash 的数据库写入；
- 没有看到完整的历史快照或页面 Diff 持久化；
- `apscheduler` 出现在依赖中，但没有确认调度器已被启动；
- `monitor_interval_minutes` 目前主要是配置项。

因此应描述为“变化检测组件和监控工作流原型”，不能直接描述成已经完成的 7×24 生产监控系统。

**成熟度：变化检测已实现；持续调度和历史持久化为部分实现。**

当前项目已有 `subscriptions` 表和订阅 CRUD 接口，但还没有：

- 定时抓取任务；
- 页面 Hash/快照保存；
- 前后版本 Diff；
- 变化类型与严重程度记录；
- 监控失败重试和通知。

### 4.2 高危变化告警

`AlertAgent` 会筛选 `HIGH` 和 `CRITICAL` 变化，然后调用通知工具发送：

- Slack Webhook；
- 钉钉 Webhook。

告警内容包含竞品、变化类型、摘要、URL、检测时间和严重程度。

项目中还存在 `send_email()`，但当前 `broadcast_alert()` 只调用 Slack 和钉钉，邮件函数没有接入统一广播入口。因此邮件能力属于部分实现。

当前项目没有外部告警通道，调研完成、失败、证据不足或竞品重大变化都不会自动发送 Slack、钉钉或邮件通知。

**成熟度：Slack/钉钉告警已实现；邮件接入和持续监控触发为部分实现。**

### 4.3 标准化 Sales Battlecard

`BattlecardAgent` 输出独立的销售战术卡：

```json
{
  "our_strengths": [],
  "our_weaknesses": [],
  "competitor_strengths": [],
  "competitor_weaknesses": [],
  "key_differentiators": [],
  "objection_handling": {},
  "elevator_pitch": ""
}
```

它面向的是销售执行，而不是完整研究报告。典型用途包括：

- 在销售会议前快速了解竞品；
- 针对客户异议生成回应；
- 形成对竞品优势和弱点的统一表达；
- 给销售提供 30 秒电梯演讲。

当前项目虽然支持销售视角，并可以生成卖点和策略建议，但没有独立的 Battlecard Schema、异议处理字段、Battlecard API 或销售卡片页面。

**成熟度：参考项目已实现；当前项目缺少独立 Battlecard 资产。**

### 4.4 显式拆分的五类 Agent 模块

该项目将职责拆成五类独立模块：

```text
MonitorAgent
ResearchAgent
CompareAgent
BattlecardAgent
AlertAgent
```

每类 Agent 有独立 Python 类、Prompt、输入输出模型和 LangGraph 节点。这样做的优点是：

- 单个 Agent 可以独立测试；
- 输入输出边界清楚；
- 便于替换某一类 Agent；
- 便于按职责组织日志和指标。

当前项目的 48 位专家主要是可被编排器引用的专家画像：系统通过 `agent_id`、技能标签和任务理由表示责任归属，但专家并不是五类可独立部署的 Agent Runtime。

这两个设计解决的问题不同：

- 参考项目强调模块职责和可替换性；
- 当前项目强调专家分工、证据责任和统一质检。

**成熟度：参考项目的模块拆分已实现；当前项目的角色画像和任务编排已实现，但没有独立 Agent Runtime。**

### 4.5 LangGraph Reflexion 质量循环

其 Python 工作流大致为：

```text
Monitor
  ├─ Alert
  └─ Research → Compare → Battlecard → Quality Check
                                             ├─ score >= 7 → END
                                             └─ score < 7 → Research
```

质量节点通过 LLM 对 Battlecard 评分，低于阈值时回到 Research。

但源码中存在一个重要限制：

- `quality_check()` 解析出 `feedback`，但状态返回值主要包含 `quality_score` 和 `reflexion_count`；
- 下一轮 Research 没有显式读取这段具体反馈；
- Research 结果使用列表追加，旧结果和新结果可能混在一起；
- 低分会触发重新研究，但不一定能定向修复质量问题。

因此它实现了“低分重跑”的图结构，尚未完全实现“根据反馈定向修复”。

当前项目的返工更细：

- 证据不足、缺少来源 → `collect`；
- 论点、维度或 Schema 问题 → `analyze`；
- 表达和结构问题 → `write`；
- 每轮都重新执行规则检查和 LLM 复审；
- 最多返工 3 次；
- 保存每轮质量记录。

**成熟度：参考项目的质量分循环已实现；反馈驱动的定向返工为部分实现。**

### 4.6 多语言参考实现

该仓库同时提供：

- Python：FastAPI + LangGraph；
- Java：Spring Boot + LangChain4j；
- Go：Gin + 自研 Pipeline。

这体现了 Agent 职责、数据模型和 Pipeline 可以跨语言映射。当前项目只有 Python 后端，并且 `backend/` 与 `api/` 是两套相近实现。

多语言不是直接的产品功能。只有在需要接入 Java 企业系统、Go 高并发服务或拆分为多语言微服务时，才有必要把这一能力列入优先级。

**成熟度：多语言代码存在；企业级跨语言协同仍需单独验证。**

### 4.7 Kafka、Elasticsearch、Redis 架构骨架

该项目的配置和 Docker Compose 包含：

- Kafka/Zookeeper：事件传递；
- Elasticsearch：历史检索；
- Redis：缓存和状态。

但源码核对后，Python 主链路主要是进程内 LangGraph 调用，没有找到：

- Kafka Producer/Consumer；
- Elasticsearch 文档写入和查询；
- Redis Hash、缓存或 checkpoint 调用；
- 真实的异步 Agent 间消息消费。

因此该部分应评价为企业级部署样板和架构表达，不应直接描述成已经落地的分布式 Agent 通信系统。

当前项目虽然使用 SQLite，扩展性有限，但任务、报告、Evidence、Trace 和专家工作量的写入链路是真实存在的。

**成熟度：配置和部署骨架已实现；基础设施实际接入未确认。**

## 6. 建议引入的能力与优先级

### 6.1 P0：写作完成后的报告完整性门禁

在当前流程中增加：

```text
write
  ↓
report_completeness_audit
  ├─ 通过 → done
  └─ 不通过 → rewrite 或 write_feedback
```

建议检查：

- 必需章节是否齐全；
- 每个竞品是否都有内容；
- 每章是否达到最小内容量；
- 正文中的 Evidence ID 是否存在；
- 关键 Claim 是否真的写进正文；
- 是否存在超出调研范围的品牌；
- 是否存在空章节、错误响应或重复段落。

该能力可以复用当前项目已有的 Evidence、Claims、Schema 和审计数据，不需要重写主流水线。

### 6.2 P0：竞品订阅的定时监控

当前项目已经有订阅表，因此可以在其上扩展：

```text
subscription
  ↓
scheduler
  ↓
抓取官网/定价/招聘/博客
  ↓
保存页面 Hash 或快照
  ↓
计算 Diff
  ↓
LLM 判断变化类型和严重程度
  ↓
写入 CompetitorChange
```

建议新增或扩展字段：

- `last_checked_at`；
- `last_success_at`；
- `previous_hash`；
- `current_hash`；
- `change_type`；
- `severity`；
- `diff_summary`；
- `monitor_error`。

第一阶段可以使用 SQLite + APScheduler，任务量增长后再考虑消息队列。

### 6.3 P0：Playwright 视觉证据

建议把截图作为正式 Evidence，而不只是报告装饰：

```json
{
  "evidence_id": "e_xxxxxxxx",
  "evidence_type": "screenshot",
  "source_url": "https://example.com/pricing",
  "screenshot_path": "artifacts/t_xxx/pricing.png",
  "brand": "竞品名",
  "captured_at": "2026-10-22T10:00:00"
}
```

实现时应沿用当前项目的 Evidence ID、品牌绑定、来源 URL 和 Trace 机制，同时增加：

- URL 公网校验；
- 重定向后的最终 URL 记录；
- 截图文件持久化；
- 截图采集失败原因；
- 报告中对截图 Evidence 的引用。

### 6.4 P1：独立 Battlecard 资产

建议增加结构化对象：

```json
{
  "competitor": "竞品名",
  "our_strengths": [],
  "our_weaknesses": [],
  "competitor_strengths": [],
  "competitor_weaknesses": [],
  "key_differentiators": [],
  "objection_handling": [],
  "target_scenarios": [],
  "avoid_scenarios": [],
  "elevator_pitch": ""
}
```

可提供：

- `POST /api/reports/{report_id}/battlecard`；
- `GET /api/battlecards/{id}`；
- 报告页的销售视角入口；
- 按竞品复制、导出或分享。

Battlecard 的每个事实型字段仍应绑定 Evidence ID，避免销售话术与事实证据脱节。

### 6.5 P1：外部告警

建议在监控和任务状态基础上接入：

- Slack；
- 钉钉；
- 邮件。

触发条件可以包括：

- 定价大幅变化；
- 产品重大更新；
- 竞品招聘方向显著变化；
- 高危舆情；
- 监控任务连续失败；
- 证据不足导致任务无法完成。

告警应写入 SQLite，并保存发送渠道、发送状态、失败原因和重试次数。

### 6.6 P1：内部资料输入

任务创建接口可增加可选的 `business_context`：

```json
{
  "our_product": "我方产品说明",
  "website_copy": "我方官网文案",
  "sales_notes": "销售笔记",
  "customer_objections": ["客户异议"],
  "internal_positioning": "内部定位"
}
```

内部资料必须与公开 Evidence 分开标识，不能因为进入同一 Prompt 就被当作公开来源，也不能参与公开来源域名数量的置信度计算。

### 6.7 P1：DOCX/PDF 交付

当前项目已经拥有结构化章节、表格和图表规格，适合在交付层增加：

- Markdown/HTML 到 DOCX；
- PDF 导出；
- 图片和图表路径归档；
- 报告版本号和生成时间；
- 导出失败记录。

### 6.8 P2：在 `collect` 内增加局部 ReAct

不建议立即把整个当前项目改成完全自由的 ReAct。更稳妥的边界是：

```text
主流水线保持固定
  ↓
collect 阶段内部运行局部 ReAct Agent
  ├─ 搜索
  ├─ 打开网页
  ├─ 判断证据缺口
  ├─ 换搜索角度
  └─ 返回 Evidence 列表
```

这样可以保留当前项目的：

- 阶段可追踪性；
- 品牌证据对齐；
- 返工路由；
- 搜索量和 Token 控制；
- SQLite 持久化。

同时利用 ReAct 解决开放式采集中的搜索策略问题。

### 6.9 不建议当前优先做：Kafka、ES、Redis 全套基础设施

当前项目的任务规模和数据量仍适合 SQLite。优先级更高的是：

1. 真实订阅调度；
2. 页面 Hash/快照保存；
3. 变化检测和告警；
4. 竞品变化历史查询。

当出现以下约束时，再考虑 Kafka、Elasticsearch 或 Redis：

- 需要多个 Monitor Worker 并发消费任务；
- 需要跨服务异步传递 Evidence 和变化事件；
- 需要大规模全文检索和聚合；
- 需要多实例共享任务状态和 checkpoint。

## 7. 最终判断

### 7.1 `competitorsmart` 的核心亮点

可以概括为：

> Agent 能自主决定如何研究，并且报告明显不完整时不会结束。

对应技术是：

- LangGraph ReAct；
- Function Calling；
- ToolNode；
- 报告完整性路由；
- Playwright 视觉取证；
- Pandoc DOCX 导出。

### 7.2 `competitive-intelligence-multi-agent` 的核心亮点

可以概括为：

> 将一次性竞品分析扩展到变化监控、严重事件通知和销售执行资产。

对应技术是：

- Monitor Agent；
- 页面 Hash 变化检测；
- 变化类型和严重程度分类；
- Slack/钉钉告警；
- Battlecard Schema；
- LangGraph 条件循环；
- Python/Java/Go 参考实现。

其中 Kafka、Elasticsearch、Redis 更适合作为后续企业化架构参考，当前源码不足以证明它们已经接入 Python 主流程。

### 7.3 当前项目的相对优势

当前项目已经具备以下较完整的能力：

- Evidence 唯一 ID；
- Evidence 与品牌绑定；
- Claims 引用校验；
- 规则质检与 LLM 复审；
- `collect`、`analyze`、`write` 分类返工；
- 返工次数控制和逐轮审计记录；
- Feature Tree、Pricing Model、User Persona；
- 知乎、微博、B 站、小红书、抖音等平台定向检索；
- Trace 记录模型、阶段、Prompt 摘要、Token 和决策目的；
- SQLite 报告、Evidence、任务和专家工作量持久化；
- SSE 工作台、DAG、思维流和证据流。

因此演进方向不是替换当前项目，而是组合三类能力：

```text
当前项目的 Evidence 与质量控制
        +
competitorsmart 的 ReAct、视觉取证和成稿完整性
        +
competitive-intelligence 的持续监控、告警和 Battlecard
```

这个组合能够补齐当前项目在“自主采集、持续更新、销售交付和成稿校验”方面的缺口，同时保留当前项目已经建立的证据可追溯和质量返工机制。
